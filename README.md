# ConfLlm — транскрипция и черновик протокола встречи

<!-- ConfLlm: RAG quickstart link -->
> Вопросы по конференциям, отдельный CPU-сервис embeddings, метрики
> и требования к API описаны в [руководстве RAG](docs/RAG_QUICKSTART.md).
> Embeddings-сервис запускается отдельно от основного Docker Compose.
> Совместимость с конкретным облачным провайдером требует проверки.


ConfLlm превращает запись встречи в транскрипт с говорящими и черновик
протокола с обсуждениями, решениями, задачами и ссылками на источники.
Результат можно проверить и отредактировать в веб-интерфейсе,
а затем экспортировать в DOCX и PDF.

Проект предназначен для локального использования. Сгенерированный
протокол требует проверки человеком и не является утверждённым документом.

## Возможности

- Обработка записей через веб-интерфейс или CLI.
- Выделение интервалов речи с Silero VAD.
- Распознавание речи через отдельный сервер Parakeet.
- Диаризация: определение интервалов говорящих через Nemotron.
- Объединение текста, говорящих и временных отметок.
- Определение предполагаемых имён участников с сохранением оснований.
- Извлечение фактов с привязкой к исходным репликам.
- Веб-редактирование результатов.
- Экспорт черновика протокола в DOCX и PDF.
- Сохранение промежуточных результатов и состояния обработки.
- Связь реплик транскрипта с видео и таймлайном.
- Поиск по прошлым встречам и история решений с указанием источников.
- Запуск веб-приложения и инструментов обработки в Docker.

Основной автоматический сценарий использует Parakeet. GigaAM сохранён
как отдельный экспериментальный ASR-скрипт. Whisper встречается в старых
результатах сравнения и скрипте объединения, но отдельного актуального
скрипта распознавания Whisper в проекте нет.

## Статус проверки

На одной реальной записи ранее подтверждён проход:
видео → аудио → VAD → Parakeet → Nemotron →
транскрипт со спикерами → извлечение фактов → JSON и Markdown.

Определение предполагаемых имён и экспорт DOCX/PDF проверялись отдельно
на сохранённом транскрипте.

Для Docker подтверждены:

- успешная сборка образа;
- запуск веб-приложения;
- статус контейнера `healthy`;
- ответ `200 OK` от `/api/health`;
- ручная проверка работы веб-интерфейса.

Эти проверки не означают, что полный AI-пайплайн с новой записью
проверен внутри контейнера или что чистая установка воспроизводима
на любой машине. Сквозная обработка зависит от внешних серверов моделей.

Результаты отдельных записей и тестовых фрагментов не являются
универсальной оценкой качества системы.

## Архитектура

```text
Запись встречи
      |
      v
FFmpeg: WAV, 16 kHz, mono
      |
      v
Silero VAD: интервалы речи
      |
      v
Подготовка фрагментов -> Parakeet: распознавание
      |
      +---------------- Nemotron: интервалы говорящих
      |
      v
Объединение текста, говорящих и таймкодов
      |
      v
LLM: предполагаемые имена и извлечение фактов
      |
      v
JSON / Markdown -> проверка и редактирование -> DOCX / PDF
```

| Компонент | Назначение | Где работает |
|---|---|---|
| FastAPI / Uvicorn | Веб-интерфейс и API | Приложение |
| FFmpeg | Извлечение и подготовка аудио | Приложение |
| Silero VAD / CPU PyTorch | Определение интервалов речи | Приложение |
| Parakeet | Распознавание речи | Отдельный HTTP-сервер |
| Nemotron | Диаризация | Отдельный HTTP-сервер |
| Qwen через OpenAI-совместимый API | Работа с именами и фактами | Отдельный LLM-сервер |
| python-docx / ReportLab | Экспорт документов | Приложение |
| CPU-сервис embeddings и разбиения текста | Подготовка фрагментов и векторов для RAG | Отдельный HTTP-сервер из `services/embeddings` |

Основной Docker-образ включает приложение, FFmpeg, curl, CPU-зависимости
VAD и инструменты экспорта. Он не запускает серверы Parakeet, Nemotron,
текстовой LLM и embeddings.

Текущий Docker Compose запускает только основное приложение.
CPU-сервис embeddings собирается и запускается отдельно по инструкции
в `docs/RAG_QUICKSTART.md`.

## Docker: запуск с embeddings и без них

Обычный `docker compose up --build -d` запускает приложение
без локальной embedding-модели.

Для приложения вместе с CPU-сервисом embeddings и chunking:

```bash
docker compose -f compose.yaml -f compose.rag.yaml up --build -d
```

Первый запуск скачивает веса. Сервис не запускается автоматически
только от открытия Docker Desktop.

Остановка:

```bash
docker compose -f compose.yaml -f compose.rag.yaml down
```

Остановка сохраняет веса на диске. Удаление кэша, повторное скачивание,
проверка запуска и требования к внешним серверам описаны
в [руководстве Docker RAG](docs/DOCKER_RAG.md).

Серверы текстовой LLM, Parakeet и Nemotron по-прежнему запускаются отдельно.
Выявление новых открытых вопросов остаётся экспериментальной функцией.

## Быстрый запуск на Windows

Это рекомендуемый путь, если нужно просто запустить приложение.
Python отдельно устанавливать не нужно: он уже находится в Docker-образе.

### Перед запуском: серверы для обработки видео и RAG

Docker Compose запускает веб-приложение, но **не скачивает и не запускает
модели**. Для обработки новой записи заранее запустите их отдельно:

1. **llama.cpp с Qwen** — анализирует готовый текст, предлагает имена
   и извлекает пункты протокола. Он должен предоставлять OpenAI-совместимый
   API чата.
2. **Parakeet** — переводит аудио в текст с временными отметками.
3. **Nemotron** — определяет временные интервалы говорящих.

Эти три сервера нужны для полной обработки новой записи.

Для индексации и вопросов по записям дополнительно требуется сервис
embeddings и разбиения текста. В проекте предусмотрен отдельный CPU-сервис,
который предоставляет обе функции. Его запуск описан
в [руководстве RAG](docs/RAG_QUICKSTART.md).

Без этого сервиса обычная обработка видео может работать при доступных
Parakeet, Nemotron и текстовой LLM, но построение RAG-индекса и вопросы
по записям недоступны. Для формирования ответа также нужна текстовая LLM.

Если запустить только приложение или только llama.cpp, страница откроется,
но обработка новой записи не завершится: Parakeet и Nemotron тоже обязательны.
Если нужно только открыть редактор или посмотреть уже сохранённые результаты,
серверы моделей для этого не требуются.
Сами серверы моделей устанавливаются отдельно от этого проекта.

Важно: текущий автоматический сценарий использует **Parakeet, а не Whisper**.
Whisper применялся в ранних экспериментах и сравнении; веб-загрузка его сейчас
не запускает.

### Шаг 1. Запустите Docker Desktop

Установите Docker Desktop, запустите его и дождитесь состояния «Running».
Откройте PowerShell в папке проекта — там, где находятся `compose.yaml`
и `Dockerfile`.

### Шаг 2. Создайте настройки

В PowerShell выполните:

```powershell
if (-not (Test-Path .env.docker)) {
    Copy-Item .env.docker.example .env.docker
}
```

Откройте `.env.docker` в VS Code и укажите адреса уже запущенных серверов.
В шаблоне стоят примеры портов: Qwen — `8001`, Parakeet — `8083`,
Nemotron — `8090`. Если у вас другие порты или имена моделей, замените
значения на свои. Для Docker Desktop сервер на этом же компьютере обычно
доступен по адресу `host.docker.internal`, а не `localhost`.

Заполните `LLM_MODEL` точным именем модели, которое показывает llama.cpp.
Ключ `LLM_API_KEY` должен соответствовать настройке сервера; если сервер
не проверяет ключ, оставьте любое непустое значение.
Для обычной обработки видео настройки embeddings не требуются.

Для RAG настройте отдельные параметры:

- `LLM_EMBEDDING_MODEL` — имя embedding-модели;
- `LLM_EMBEDDING_BASE_URL` — базовый адрес API embeddings;
- `LLM_EMBEDDING_API_KEY` — ключ доступа согласно настройке сервиса;
- `LLM_CHUNKING_URL` — адрес сервиса разбиения текста.

Пример настроек и команды запуска CPU-сервиса находятся
в `.env.docker.example` и `docs/RAG_QUICKSTART.md`.
Наличие текстовой LLM не означает поддержку embeddings
или используемого проектом API разбиения текста.

Не публикуйте `.env.docker` и настоящий ключ доступа.

### Шаг 3. Соберите и запустите приложение

В той же папке PowerShell выполните:

```powershell
New-Item -ItemType Directory -Force data, outputs, web_jobs | Out-Null
docker compose up --build -d
```

При первом запуске Docker скачает базовый образ и установит зависимости;
это может занять время. Команда соберёт образ и запустит приложение.

### Шаг 4. Проверьте, что приложение запустилось

```powershell
docker compose ps
Invoke-RestMethod http://localhost:8000/api/health
```

В ответе API должно быть `status: ok`, а контейнер `app` должен перейти
в состояние `healthy`. Затем откройте в браузере:

- http://localhost:8000/ — веб-приложение;
- http://localhost:8000/docs — список API-методов.

Проверка `/api/health` подтверждает только запуск веб-приложения.
Она не проверяет доступность Qwen, Parakeet и Nemotron.

### Шаг 5. Обработайте запись

1. В блоке «Новая запись» выберите видео и нажмите «Загрузить и обработать».
2. Дождитесь сообщения о завершении; во время обработки не выключайте Docker.
3. Выберите запуск и нажмите «Открыть».
4. Сверьте реплики и пункты протокола с источниками, исправьте ошибки.
5. Сохраните редакцию и нажмите «Экспорт DOCX/PDF».

Автоматический документ — черновик. Перед отправкой обязательно проверьте
решения, исполнителей, сроки, имена и источники.

### Остановка

Чтобы остановить приложение, не удаляя записи и результаты:

```powershell
docker compose down
```

Данные остаются в папках `data`, `outputs` и `web_jobs`. Не удаляйте их,
если хотите сохранить записи и результаты. Чтобы снова запустить приложение,
выполните `docker compose up -d`.

Compose публикует веб-приложение только на этом компьютере (`127.0.0.1`).
Не открывайте его или серверы моделей в интернет без отдельной защиты.

### Вариант запуска из WSL2

Этот вариант тоже использует Docker Desktop: не устанавливайте второй Docker
внутрь WSL. В Docker Desktop откройте **Settings → Resources → WSL Integration**
и включите интеграцию для своего дистрибутива Linux. После этого откройте
терминал WSL2.

Перейдите в папку проекта. Если он хранится на диске C:, путь будет выглядеть
примерно так:

```bash
cd "/mnt/c/Users/ИМЯ_ПОЛЬЗОВАТЕЛЯ/Desktop/LLM/ConfLlm"
```

Замените `ИМЯ_ПОЛЬЗОВАТЕЛЯ` на имя папки пользователя Windows. Для более
быстрой сборки удобнее держать рабочую копию проекта внутри файловой системы
WSL, например `~/projects/ConfLlm`, а не в `/mnt/c/...`.

Убедитесь, что Docker Desktop запущен и команда доступна из WSL:

```bash
docker compose version
```

Если команда не найдена, сначала включите WSL Integration в Docker Desktop.
Затем создайте файл настроек, если его ещё нет:

```bash
if [ ! -f .env.docker ]; then
  cp .env.docker.example .env.docker
fi
```

Откройте `.env.docker` в VS Code и заполните адреса работающих серверов
моделей так же, как описано в шаге 2 выше. Для обработки из контейнера
используйте адреса, доступные именно контейнеру; на Docker Desktop это обычно
`host.docker.internal`, а не `localhost`.

Соберите и запустите приложение:

```bash
mkdir -p data outputs web_jobs
export LOCAL_UID="$(id -u)"
export LOCAL_GID="$(id -g)"
docker compose up --build -d
```

Проверка и использование те же, что в Windows PowerShell:

```bash
docker compose ps
```

Откройте в браузере Windows http://localhost:8000/ или проверьте API
по адресу http://localhost:8000/api/health. Для просмотра журнала запуска
из WSL выполните `docker compose logs -f app`; остановить просмотр журнала
можно клавишами Ctrl+C — контейнер при этом продолжит работать.

Остановить приложение можно из WSL:

```bash
docker compose down
```

Выберите либо PowerShell, либо WSL2 и выполняйте команды запуска в одном
месте. Не запускайте два независимых экземпляра приложения одновременно.

## Что происходит после загрузки видео

1. Загруженный файл сохраняется в `web_jobs`; оригинал нужен для плеера.
2. **FFmpeg** извлекает из видео звуковую дорожку и приводит её к формату,
   удобному для обработки: WAV, один канал, 16 кГц.
3. **Silero VAD** отмечает участки, где есть речь. Он не распознаёт слова;
   его задача — помочь не отправлять длинные паузы на распознавание.
4. Программа нарезает отмеченное аудио на небольшие куски и записывает,
   где каждый кусок находился в исходной записи.
5. **Parakeet** распознаёт слова и их таймкоды.
6. **Nemotron** отдельно размечает, когда говорит каждый участник.
7. Программа сопоставляет слова и интервалы говорящих. Так появляются
   реплики вида «speaker_1: текст». Если надёжного совпадения нет,
   говорящий может остаться `unknown`.
8. **Qwen через llama.cpp** анализирует уже готовый транскрипт: предлагает
   возможные имена и выделяет решения, задачи, риски и вопросы. Имена
   остаются предположениями, пока человек их не проверит.
9. Программа добавляет ссылки на исходные реплики, сохраняет результаты,
   создаёт DOCX/PDF и показывает редактор.
10. В редакторе реплика, таймлайн и видео связаны по времени: нажмите
    на реплику или источник, чтобы перейти к этому моменту записи.

Промежуточные файлы помогают понять, на каком этапе возникла ошибка:
`data/meetings` содержит рабочее аудио и куски, а `outputs` — транскрипт,
факты, статус этапов и документы.

## Как проект развивался

Если коротко, сначала проверяли локальную языковую модель, а потом строили
обработку встречи вокруг видео и аудио:

1. **llama.cpp + Qwen.** llama.cpp запускает Qwen как локальный HTTP-сервис.
   Скрипт `check_llm.py` проверяет, отвечает ли модель. Он не распознаёт
   видео и не создаёт протокол. `check_protocol_example.py` отдельно
   проверяет, умеет ли модель извлекать заданные поля из готового текста.
2. **Первые эксперименты с распознаванием.** Whisper использовался на ранней
   версии записи, затем результаты сравнивались с GigaAM и Parakeet.
   Это описано в `benchmarks/ASR_COMPARISON.md`. Скачивание или запуск
   Whisper не является частью текущей веб-обработки.
3. **FFmpeg и VAD.** FFmpeg вытаскивает аудио из видео. Silero VAD находит
   места, где звучит речь; затем программа готовит небольшие фрагменты,
   сохраняя их исходные временные позиции.
4. **Текущий ASR-конвейер.** В основном запуске Parakeet распознаёт речь,
   Nemotron размечает говорящих, а программа объединяет слова, время и
   говорящих в реплики. То есть Whisper не нужно искать в кнопке запуска:
   её заменяет Parakeet.
5. **Qwen после распознавания.** Когда текст уже готов, Qwen предлагает
   имена и извлекает решения, поручения, риски и вопросы. Код проверяет
   структуру ответа и ссылки на реплики.
6. **Проверка человеком и новые функции.** Добавлены веб-редактор,
   экспорт документов, переход от реплики к видео, затем память решений
   и RAG-поиск по прежним материалам.

Запись и её расшифровка — это входные данные. Whisper, Parakeet и Qwen —
разные модели с разными задачами: распознавание речи делает Parakeet,
а Qwen анализирует получившийся текст.

## Что уже добавлено после основного конвейера

- Редактор позволяет проверять источники, править пункты и участников,
  сохранять редакцию и экспортировать документы.
- Структурированная память хранит решения, поручения и открытые вопросы,
  позволяет просматривать связанные источники и историю решений.
- RAG позволяет искать по проиндексированным материалам.
  Веб-интерфейс вопросов использует фрагменты расшифровок для формирования
  ответа текстовой LLM с цитатами. Перед использованием нужно отдельно
  запустить embeddings-сервис и построить индекс.
- Сходство решений между встречами определяется эвристически, поэтому
  найденные изменения и причины нужно проверять по источникам.

Напоминания, отправка протоколов в мессенджеры и автоматический агентский
цикл в текущем пайплайне не реализованы.

### Синхронизация видео и транскрипта

В редакторе для выбранного запуска доступны исходное видео и таймлайн
распознанных реплик. Сегмент на шкале, строка реплики и ссылка на источник
перемещают видео к началу соответствующего таймкода; во время воспроизведения
активная реплика подсвечивается. Видео отдаётся по
`GET /api/meetings/{meeting_id}/{run_id}/video` с поддержкой byte-range
запросов браузера. Для защиты от чтения посторонних файлов API обслуживает
только существующие видео внутри каталога проекта.
Для запуска CLI видео за пределами каталога проекта может быть доступно
для обработки, но веб-плеер не будет его показывать. Таймкоды считаются
от начала извлечённого аудио; отдельная компенсация смещения аудиодорожки
относительно видеодорожки пока не выполняется.

### Память решений и поиск по протоколам

API материализует локальную структурированную память в
`data/meeting_memory.sqlite3`: решения и их версии, открытые вопросы,
поручения и ссылки на исходные факты/реплики. Память строится из результатов
в `outputs/`. Если сохранена редакция протокола с `revision > 0`, именно её
пункты используются при синхронизации памяти вместо исходных фактов.
Статусы вопросов и поручений сохраняются между синхронизациями.

- `POST /api/memory/sync` — обновить память из результатов встреч.
- `GET /api/memory/reasoning?topic=...` — текущие решения, версии и изменения.
- `GET /api/memory/reasoning?decision_id=...` — история одного решения.
- `GET /api/memory/items?kind=open_question&status=open` — открытые вопросы;
  `kind` также принимает `task`.
- `PATCH /api/memory/items/{task|open_question}/{item_id}` с JSON
  `{"status":"completed"}` или `{"status":"resolved"}` — изменить статус.
- `POST /api/rag/index` — перестроить локальный векторный индекс.
- `POST /api/rag/query` — поиск; кроме `question` и `top_k` можно передать
  `meeting_id`/`meeting_ids`, `topic`, `decision_id` и `source_types`.

RAG-индекс строится по транскрипту и по фактам из `facts.json`. Если для
запуска есть сохранённая редакция с `revision > 0`, вместо автоматических
фактов индексируются пункты этой редакции. Для вопросов и задач сохраняются
ссылки на ID исходных реплик и версия редакции.

Каждый результат поиска содержит тип, встречу/запуск и ссылку `source_url`;
факты связываются со стабильным ID решения, включая связанные риски и другие
факты. Список `source_types` принимает `utterance`, `decision`, `task`, `risk`,
`open_question`, `proposal`, `discussion`, `fact`, `document`.

Поиск через `/api/rag/query` и генерация ответа в интерфейсе вопросов —
разные сценарии.

Индекс может содержать реплики, факты и пункты сохранённой редакции.
Однако текущий endpoint генерации ответа использует только источники
типа `utterance`, то есть фрагменты расшифровок.

Структурированные решения, задачи и их версии не подключены
как отдельные источники для генерации ответа. Наличие памяти решений
не означает, что веб-вопросы используют всю её структуру.

«Почему изменилось» возвращает связанные источники между версиями, но не
объявляет причинность доказанной. Совпадение тем между встречами определяется
эвристически; одинаковая метка вроде «вариант A» помогает связать записи,
а общих слов «решение» или «вариант» недостаточно. Перед использованием
истории проверьте ссылки на протокол и реплики.

### Версии запусков и отчёты качества

Каждый новый pipeline-run сохраняет `run_manifest.json` рядом со статусом
запуска. В нём записываются SHA-256 исходного видео, версии схем, хеши
промптов и файлов реализации, а также точные хеши Pydantic-схем извлечения
фактов и имён. Для форматов транскрипта и редакции записываются версии схем
и хеши реализующих их файлов. Также сохраняются названия моделей, безопасные адреса сервисов
(без логинов, ключей и query-параметров), параметры обработки, версии Python,
статусы этапов и их длительность. Если сервер Nemotron не сообщает версию
модели, манифест отмечает это явно. Секреты и содержимое записи в манифест
не копируются.

После обработки рядом появляется `quality_report.json`: длительность аудио,
счётчики VAD/ASR/диаризации/реплик/фактов, неизвестные говорящие, отметки
проверки, пропуски блоков, повторы запросов, ошибки и наличие экспортов.
Это диагностика покрытия и работы этапов, **не оценка точности** моделей.

В `evals/datasets/rag_quality_v1.json` хранится небольшой версионированный
набор примеров: исходные реплики, проверенные факты, вопросы, эталонные ответы
и ID фактов-источников. Он составлен по включённому учебному примеру
`examples/meeting_001.txt`; это smoke-набор, а не репрезентативная оценка
реальных встреч. Не добавляйте записи встреч в Git без обезличивания,
разрешения и ручной проверки меток.

Запускайте проверки из Docker-контейнера, когда сервис LLM и модель embeddings
доступны:

```powershell
docker compose exec app python -m evals.evaluate_rag --top-k 3 --output data/evaluation_reports/rag_quality.json
docker compose exec app python -m evals.evaluate_facts --output data/evaluation_reports/facts_quality.json
```

RAG-оценка сообщает Recall@k, MRR и Precision@k для поиска правильных
источников. Она проверяет retrieval — поиск релевантных фрагментов, —
а не качество ответа текстовой LLM.

В приложении есть отдельный сценарий генерации ответа с цитатами,
но текущий evaluator не оценивает его фактическую точность, полноту,
соответствие цитатам или корректность отказа при отсутствии данных.

Fact-оценка запускает экстрактор с текущей моделью и сравнивает категории,
ссылки на реплики, а для задачи — исполнителя и срок с эталоном. Её результаты
могут меняться от модели и промпта; запускайте её после таких изменений.

При обновлении промпта, схемы или ожидаемого ответа повышайте
`dataset_version`, проверяйте метки вручную и сохраняйте старую версию
для сравнения.

### Почему пока без Qdrant

В проекте оставлен локальный SQLite-индекс с cosine-поиском. На текущем
масштабе не подтверждена проблема, которую оправдывал бы отдельный Qdrant:
сначала соберите размер индекса и время поиска на обезличенном корпусе,
запустите RAG benchmark и проверьте фильтры по встречам/источникам. Переход
имеет смысл, если измерения покажут неприемлемую задержку, объём или проблемы
параллельного доступа. Пока Qdrant не добавлялся и не требуется для запуска.

## Локальная разработка

Основное окружение проекта — Python 3.12, Linux / Ubuntu / WSL.
Прямой запуск backend из обычного Windows Python сейчас не поддерживается:
очередь веб-заданий использует Linux-модуль `fcntl`. На Windows используйте
Docker Desktop; для разработки без Docker — Linux или WSL.

FFmpeg и curl устанавливаются отдельно. Например, в Ubuntu:

```bash
sudo apt-get update
sudo apt-get install -y \
  python3-venv ffmpeg curl fonts-dejavu-core libgomp1 libsndfile1
```

Создание Python-окружения:

```bash
python3 -m venv .venv
source .venv/bin/activate

python -m pip install \
  -r requirements-torch.txt \
  --index-url https://download.pytorch.org/whl/cpu

python -m pip install \
  -r requirements.txt \
  -r requirements-export.txt \
  -r web_requirements.txt \
  -r requirements-vad.txt \
  -c requirements-torch.txt

python -m pip check
```

Этот набор соответствует основной схеме зависимостей Dockerfile.
Зависимости альтернативной ветки GigaAM требуют отдельной подготовки.
Наличие одного `requirements.txt` не означает наличие всего окружения.

Подготовьте `.env`, не перезаписывая существующий:

```bash
if [ ! -e .env ]; then
  cp .env.example .env
fi
```

Заполните настройки LLM и адреса серверов.
Для CLI адреса Parakeet и Nemotron можно передать явно.

Запуск веб-приложения:

```bash
python -m uvicorn backend.main:app --reload --port 8000
```

Не запускайте локальное приложение и контейнер одновременно
над одними и теми же рабочими данными.

После подготовки окружения, конфигурации и серверов моделей:

python run_pipeline.py \

Автоматическое продолжение всего запуска после сбоя пока не реализовано.

проверяйте соответствие исходной записи и настроек.

## Источники, предполагаемые имена и проверка результата

Экстрактор получает от LLM идентификаторы исходных реплик.
Оригинальные тексты, говорящие и таймкоды добавляются программно.
Ошибки структуры и ссылок вызывают ограниченные повторные попытки.
Неполный результат явно помечается и возвращает ненулевой код завершения.

Имена участников являются предположениями, а не подтверждённой
идентификацией личности. Для них сохраняются основания и статусы.
Неизвестные имена могут оставаться `unresolved`,
противоречащие кандидаты — `conflict`.

Исходные идентификаторы говорящих сохраняются в транскрипте и источниках.
В проекте предусмотрена резервная логика для имён; её наличие
не гарантирует продолжение при любой ошибке этапа.

Наличие цитаты не доказывает правильность пересказа.
Перед использованием документа проверьте:

- соответствие фактов исходным репликам;
- решения и поручения;
- исполнителей и сроки;
- имена участников;
- отсутствие повторов и потерянного контекста.

Таймкоды источников относятся к репликам, а не обязательно
к точным границам процитированного фрагмента.

3. Если есть совместимые и разрешённые к показу результаты,

3. Загрузите новую запись без конфиденциальных данных.
4. Дождитесь завершения обработки.
5. Проверьте факты и предполагаемые имена.

До публикации примеров и скриншотов проверьте права на материалы
и отсутствие персональных данных.

## Ограничения и безопасность

- Приложение рассчитано на локальное использование и не имеет авторизации.
- Не публикуйте API приложения и серверы моделей в интернете без защиты.
- Одновременно поддерживается одна веб-обработка.
- В веб-загрузке предусмотрен лимит 1 GiB.
- Веб-интерфейс принимает видео MP4, MKV, MOV, WEBM, AVI и M4V.
  Внутренний WAV не означает поддержку отдельной загрузки аудио через UI.
- Полная запись и все извлечённые факты требуют ручной проверки.
- Обработка блоками может терять контекст и создавать повторы.
- Предполагаемые имена могут быть неверными или не определиться.
- Автоматическое продолжение всего пайплайна после сбоя не реализовано.
- Для PDF нужен шрифт с поддержкой кириллицы;
  Dockerfile устанавливает DejaVu.
- Основные зависимости закреплены, но полного транзитивного lock-файла нет.
- Доступность CPU-пакетов зависит от версии Python и индекса PyTorch.
- Лицензии моделей, библиотек и права на входные материалы
  проверяются отдельно.

## Проверка открытых вопросов

Доступен экспериментальный агент с ручным запуском:
он проверяет выбранный вопрос, получает источники, формирует
предложение ответа и сохраняет журнал действий.

Два режима:
- «Исходный диалог» — вопрос и ближайшие реплики исходного запуска;
- «Все проиндексированные материалы» — выбор поиска по расшифровкам,
  документам и структурированной памяти.

Ответы требуют проверки человеком. Агент не изменяет протокол
и не закрывает вопросы автоматически.
Выявление новых вопросов остаётся экспериментальным:
анализ ограничен фрагментом и может предложить уже отвеченный вопрос.

сценария с настоящими сервисами моделей. Это не универсальная оценка
качества и не подтверждение установки из чистого клона.
