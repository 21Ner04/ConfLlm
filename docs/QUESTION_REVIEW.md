# Агент проверки вопросов

## Статус

Экспериментальная рабочая версия с ручным запуском.
Агент проверяет выбранный вопрос, получает источники, формирует
предложение ответа и сохраняет журнал действий.
Он не изменяет протокол и не закрывает вопрос автоматически.

Выявление новых открытых вопросов — отдельная экспериментальная функция.
Она может предложить вопрос, на который уже ответили в другой части записи.
Подтверждение человеком обязательно.

## Требования

- Работающее приложение и настроенная текстовая LLM.
- Для режима «Исходный диалог» — доступная расшифровка завершённого
  запуска и сохранённые реплики-основания вопроса.
- Для режима «Все проиндексированные материалы» — построенный индекс,
  доступный embeddings-сервис и необходимые настройки поиска.
- Для построения индекса также требуется настроенное разбиение текста.

Используется текущая текстовая LLM проекта. Отдельная агентская модель
не требуется. Основной Compose не запускает все серверы моделей.

Настройка сервисов: [руководство RAG](RAG_QUICKSTART.md).

## Работа в интерфейсе

1. Нажмите «Обновить вопросы».
2. Выберите открытый вопрос.
3. Выберите область ответа.
4. Нажмите «Запустить агента».
5. Проверьте ответ по источникам.

Ответ отображается сразу. Источники, сведения о предложении и журнал
раскрываются отдельно. Кнопка быстрой проверки из интерфейса удалена;
старый API ручной проверки сохранён.

### Исходный диалог

Агент получает инструмент read_question_context.
Читается исходная реплика и до двух следующих реплик того же запуска.
Окно прекращается перед следующей репликой со знаком вопроса.

Это консервативная эвристика: она может остановить окно на риторическом
вопросе или пропустить ответ, который находится значительно дальше.
Другие встречи, память и документы в этом режиме не используются.

### Все проиндексированные материалы

Модель выбирает доступные инструменты:

- search_transcripts — расшифровки;
- search_documents — документы существующего индекса;
- search_memory — свидетельства структурированной памяти.

Поиск по расшифровкам расширяется соседними репликами.
Одинаковые текстовые окна из копий записи подавляются в рамках выдачи.
Источники сохраняют собственные идентификаторы встречи и запуска.

Поиск памяти лексический и ограничен 5000 записями свидетельств.
Исторические сведения не считаются автоматически актуальными.
Совпадение speaker_2 в разных встречах не доказывает одну личность.

## Как работает цикл

Планировщик выбирает действие, получает результат и решает,
продолжить поиск или завершить работу.

Ограничения текущего запуска:
- до пяти решений планировщика;
- до трёх вызовов инструментов;
- до 18 источников в состоянии агента;
- текст отдельного источника ограничивается 3000 символами.

Повторный одинаковый поиск не выполняется. После него планировщику
разрешается только финальное решение по уже полученным свидетельствам.
Если требование проигнорировано, результат остаётся incomplete.

Лимит времени ядра проверяется между вызовами и не прерывает работающий
сетевой запрос. Финальная проверка ответа выполняется отдельно и может
увеличить общее время.

## Проверка ответа и статусы

Для сформированного ответа выполняется дополнительный вызов той же LLM:
проверяются релевантность и подтверждение каждого утверждения.
Не прошедшие проверку утверждения исключаются.

Эта проверка не гарантирует точность. В ходе разработки модель уже
ошибочно признавала релевантным ответ на соседний вопрос интервью.

Статусы:
- answered — сохранён кандидат ответа, а не подтверждённое решение;
- insufficient_sources — недостаточно оснований в проверенных источниках;
- incomplete — проверка не завершена или ответ не прошёл контроль;
- error — ошибка планировщика или формата действия.

Сообщение «бюджет не утверждён» может быть корректным кандидатом ответа,
если прямо подтверждено источником. Это не закрывает вопрос о сумме бюджета.

## Выявление новых вопросов

1. Откройте обработанную встречу.
2. Нажмите «Найти вопросы в открытой встрече».
3. Проверьте предложенную формулировку и исходные реплики.
4. Подтвердите подходящий вопрос или отклоните предложение.
5. Подтверждённый вопрос появится в общем списке.

Анализ ограничен первыми 40 подходящими репликами и 12000 символов.
При ошибке переполнения контекста запросы адаптивно разделяются.
Покрытие и частичность анализа указываются в результате.

Формулировка нового вопроса должна присутствовать в процитированном тексте.
Это защита от выдуманных формулировок, а не доказательство,
что вопрос действительно остался без ответа.

Нет полного анализа всей длинной записи и надёжного сопоставления
вопросов с ответами между всеми фрагментами. Смысловые дубли вопросов
автоматически не объединяются.

## Хранение

Все базы находятся в локальном data/:

- meeting_memory.sqlite3 — структурированная память;
- question_reviews.sqlite3 — предложения ответов;
- question_agent_runs.sqlite3 — проходы, источники, оценки и журналы;
- question_discoveries.sqlite3 — найденные и подтверждённые вопросы.

Подтверждённые вопросы хранятся отдельно от пересоздаваемых таблиц памяти.
Повторное подтверждение не должно сбрасывать изменённый статус вопроса.

Одинаковые предложения не сохраняются повторно.
Их дата сохранения может быть старше текущего агентского прохода.
Актуальные метрики прохода находятся в журнале агента.

Базы содержат тексты и потенциально конфиденциальные сведения.
Не добавляйте data/ и пользовательские журналы в Git.

## API

- POST /api/question-agent/run
- GET /api/question-agent/runs
- GET /api/question-reviews
- POST /api/question-reviews/run — сохранённый старый сценарий
- POST /api/question-discoveries/run
- GET /api/question-discoveries
- POST /api/question-discoveries/{suggestion_id}/accept
- POST /api/question-discoveries/{suggestion_id}/reject

Пример запуска агента:

```json
{
  "question_id": "ID_ВОПРОСА",
  "answer_scope": "source_dialogue"
}
```

Значения answer_scope: source_dialogue или all_meetings.
Если параметр API не передан, используется all_meetings.
В интерфейсе изначально выбран source_dialogue.

Статус вопроса можно изменить существующим API:
PATCH /api/memory/items/open_question/{question_id}.
Завершённого интерфейсного процесса принятия ответа с версионированием
и автоматическим закрытием вопроса пока нет.

## Подтверждённые проверки

5 ноября 2026 года:
- 111 автоматических тестов прошли за 13,06 секунды.
- git diff --check завершился без замечаний.
- Docker-образ собран и приложение запущено.
- Пройден изолированный smoke-прогон с настоящими chunking,
  embeddings и текстовой LLM на четырёх учебных сценариях:
  исходный диалог, ответ в другой встрече, неутверждённый бюджет
  без выдуманной суммы, отсутствие сведений о выручке.
- Подтверждены сохранение открытых статусов и восстановление
  после попытки повторного поиска.

Повторный live-прогон:

```bash
docker compose exec -T app python -m evals.smoke_question_agent
```

Он создаёт временные встречи и базы в отдельном процессе.
Рабочие встречи и память не используются.
Вопросы для fixtures задаются явно: этот прогон не оценивает
качество автоматического выявления вопросов.
Сценарий вызывает обработчики напрямую, а не по HTTP.

Автоматические тесты запускаются из подготовленного dev-окружения:

```bash
.venv/bin/python -m pytest -q tests
```

## Что не реализовано или не подтверждено

- Фоновый запуск после новых встреч и очередь перепроверки.
- Продолжение работы с учётом всех уже проверенных версий материалов.
- Интернет-поиск.
- Надёжное автоматическое обнаружение противоречий.
- Полный анализ незакрытых вопросов по всей длинной записи.
- Гарантированная фактическая точность проверяющей LLM.
- Универсальное управление токеновым бюджетом всех этапов.
- Распределённая блокировка для нескольких процессов приложения.
- Установка и запуск из чистого клона на другой машине.

Текущая блокировка рассчитана на один процесс приложения.
Не запускайте несколько независимых экземпляров над общими данными.
